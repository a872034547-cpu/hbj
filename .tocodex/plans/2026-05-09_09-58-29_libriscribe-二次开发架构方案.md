# Libriscribe 二次开发架构方案

## 一、现有代码分析总结

### 当前架构
- **入口**: CLI（Typer + Rich），`main.py` 约 845 行
- **代理模式**: `Agent` 基类 → 12 个专用代理（ConceptGenerator, Outliner, ChapterWriter, Editor, StyleEditor, ContentReviewer, Researcher, Formatting, PlagiarismChecker, FactChecker, CharacterGenerator, Worldbuilding）
- **编排**: `ProjectManagerAgent` 顺序调用各代理
- **状态管理**: `ProjectKnowledgeBase`（Pydantic 模型）→ JSON 文件持久化
- **LLM**: 统一 `LLMClient`，支持 OpenAI/Claude/Gemini/DeepSeek/Mistral/OpenRouter
- **输出**: Markdown / PDF（fpdf）

### 需要新增的核心能力
| 能力 | 现状 | 目标 |
|------|------|------|
| RAG 向量检索 | ❌ 无 | ChromaDB + 文档解析 |
| LangGraph 状态机编排 | ❌ 无 | 有状态多代理循环 |
| Web UI | ❌ 仅 CLI | Streamlit 交互界面 |
| 引用溯源 | ❌ 无 | Structured Output + GB/T 7714 |
| DOCX/LaTeX 导出 | ❌ 无 | python-docx + Pandoc |
| 术语表/全局记忆 | ❌ 无 | 术语字典 + 风格向量 |
| 版本历史 | ❌ 无 | 检查点 + 回滚 |
| 人机协作 | 基础 confirm | Web UI 编辑/重新生成 |

## 三、分阶段实施计划

### 阶段 1：核心基础设施（RAG + 状态增强 + 记忆系统）

**1.1 RAG 模块** (`src/libriscribe/rag/`)
- `document_loader.py`: 使用 `Unstructured` 解析 PDF/Word/Excel，提取文本分块
- `embeddings.py`: 封装嵌入模型（OpenAI Embedding / 本地 sentence-transformers）
- `vector_store.py`: ChromaDB 本地向量数据库，支持增量添加/查询
- `retriever.py`: 混合检索（向量相似度 + 关键词），返回 top-k 片段带溯源信息

**1.2 全局记忆** (`src/libriscribe/memory/`)
- `terminology.py`: 术语表（JSON 持久化），支持添加/查询/批量替换
- `summary_manager.py`: 分层摘要 — 每章生成后自动摘要，跨章时只传"前 N 章关键摘要 + 术语表"
- `version_history.py`: 基于文件的检查点系统，每次重大操作保存快照，支持回滚

**1.3 知识库扩展** (`knowledge_base.py`)
- 新增字段：`terminology: Dict[str, str]`, `references: List[Citation]`, `chapter_summaries: Dict[int, str]`, `rag_documents: List[str]`
- 新增 `Citation` 模型：`{sentence, source, page, quote_original, formatted_ref}`

### 阶段 2：LangGraph 工作流编排

**2.1 状态定义** (`workflow/state.py`)
```python
class BookWritingState(TypedDict):
    project: ProjectKnowledgeBase
    current_chapter: int
    chapter_content: str
    review_result: dict
    iteration_count: int
    rag_context: list
    terminology: dict
    chapter_summaries: dict
    human_feedback: str
    status: str  # "planning" | "writing" | "reviewing" | "editing" | "completed"
```

**2.2 节点实现** (`workflow/nodes.py`)
- `planner_node`: 解析目录 → 细化章节树
- `research_node`: RAG 检索相关资料
- `writer_node`: 分节生成（注入前文摘要 + 术语表 + RAG 片段）
- `critic_node`: 逻辑检查、术语一致性、学术规范
- `editor_node`: 风格统一、润色
- `human_review_node`: 人工审核中断点（LangGraph interrupt）

**2.3 条件边** (`workflow/edges.py`)
- `should_iterate`: critic 评分 < 阈值且 iteration < 3 → 回到 writer
- `needs_human_review`: 用户设置为 Human 模式 → interrupt
- `chapter_complete`: 进入下一章

**2.4 主图** (`workflow/graph.py`)
```
START → planner → [对每章循环]:
    research → writer → critic → (条件) → editor → human_review → 下一章
                         ↑        ↓
                         └── iterate ┘
→ 全书整合 → END
```

### 阶段 3：代理增强

**3.1 ChapterWriterAgent 增强**
- 生成时注入：前 N 章摘要 + 术语表 + RAG 检索片段
- Structured Output 强制 JSON：`{"content": "...", "citations": [{"sentence": "...", "source": "..."}]}`

**3.2 新增 CitationAgent** (`agents/citation_agent.py`)
- 从生成内容中提取引用
- 格式化为 GB/T 7714
- 验证引用来源是否存在

**3.3 新增 CriticAgent** (`agents/critic_agent.py`)
- 逻辑一致性检查
- 术语统一性检查
- 学术规范检查
- 输出评分 + 具体修改建议

**3.4 LLMClient 增强**
- 支持 Structured Output（JSON Schema 约束）
- 支持成本优化：初稿用低成本模型，关键章节用顶级模型

### 阶段 4：Web UI

**4.1 Streamlit 应用** (`web/app.py`)
- 项目仪表盘：创建/加载项目，查看进度
- 大纲管理：树状目录，拖拽排序，编辑章节/场景
- 章节编辑器：富文本编辑，重新生成/续写/润色
- 聊天式指令：自然语言控制（"把第3章术语X统一为Y"）
- 版本历史：查看/回滚/对比

**4.2 组件** (`web/components/`)
- `chapter_tree.py`: 树状目录导航组件
- `diff_viewer.py`: 版本对比（类似 Git diff）
- `progress_bar.py`: 全书生成进度

### 阶段 5：导出增强

**5.1 DOCX 导出** (`export/docx_export.py`)
- python-docx 生成，支持标题层级、页眉页脚、目录

**5.2 LaTeX 导出** (`export/latex_export.py`)
- 生成 LaTeX 源文件，可选通过 Pandoc 编译为 PDF

**5.3 参考文献** (`export/reference_formatter.py`)
- GB/T 7714 格式化
- 自动生成参考文献列表

## 五、实施优先级

1. **阶段 1**（RAG + 记忆 + 状态扩展）— 基础，其他阶段依赖
2. **阶段 2**（LangGraph 工作流）— 核心编排

## 六、关键设计决策

1. **保留原有 CLI 入口**：`main.py` 不删除，新增 `web/app.py` 作为 Web 入口
2. **渐进式迁移**：先在 `workflow/` 中用 LangGraph 重写编排逻辑，`project_manager.py` 保留作为兼容层
3. **RAG 用 ChromaDB**：本地部署，无需外部服务，适合单机场景
4. **UI 用 Streamlit**：快速原型，Python 原生，后续可迁移到 Next.js
5. **状态持久化**：JSON 文件 + ChromaDB，不引入 PostgreSQL/DynamoDB（降低部署复杂度）
