# DOC/OLE 二进制乱码证据片段修复

## 问题

用户在“证据片段样例”中看到大量乱码，例如：

```text
ÐÏà¡±á ... Root Entry ... WordDocument ...
```

这说明上传文件虽然扩展名是 `.docx`，但实际内容是旧版 Word/OLE 二进制结构或非合法 DOCX。此前兜底逻辑把二进制文件按文本读入，导致 OLE 结构被写入 RAG 证据库。

## 修改

- 修改 [`libriscribe/src/libriscribe/rag/document_loader.py`](../libriscribe/src/libriscribe/rag/document_loader.py)：
  - `.docx` 继续优先使用 `unstructured` / `python-docx` 解析。
  - `.doc` 现在走 `_load_doc()`，不再按普通文本兜底索引二进制 OLE。
  - 新增 `_is_probably_binary_text()`：识别 `ÐÏ...`、`Root Entry`、空字节、替换字符比例过高、可读字符比例过低等明显二进制乱码。
  - 新增 `_clean_extracted_text()`：过滤控制字符，并在疑似二进制时返回空文本，阻止进入证据库。
  - 新增 `is_usable_text()`：用于清理已有项目数据和后续校验。
- 修改 [`libriscribe/src/libriscribe/rag/vector_store.py`](../libriscribe/src/libriscribe/rag/vector_store.py)：延续上一轮 ChromaDB metadata 兼容修复。


说明如果用户上传的是可读文本但误命名为 `.docx`，仍可被合理索引。

```text

```

说明当前项目中的乱码来源和乱码证据片段已清空。

## 使用建议

如果资料本身是旧版 `.doc` 或被错误命名的 Word 二进制文件，请先用 Word/WPS 另存为合法 `.docx`、`.pdf` 或 `.txt` 后重新上传；程序现在会阻止不可读二进制乱码进入 RAG 证据库。
